# 첫 파일 변환 테스트 버전

[English](../test-version.md) | [한국어 README](README.md)

## 구현한 사용 흐름

영상 하나를 선택하거나 실행 파일에 끌어놓으면 HDR MKV 파일을 원본 옆에 저장한다. 명령줄에서는 입력·출력 경로, 어댑터, FFmpeg 위치, 테스트할 최대 프레임 수를 선택할 수 있다. NVEncC는 사용하지 않는다.

실제 변환은 FFmpeg 디코드 → NV12 또는 P010 업로드 → NVIDIA D3D11 HDR 확장 → RGB10A2 readback → 명시적 BT.2020 NCL P010 변환 → FFmpeg의 NVENC HEVC Main10 → 오디오 stream copy 순서다. 테스트 버전은 정확성을 우선하여 CPU 왕복을 허용했다. GPU 전용 디코드·인코드 연결은 후속 최적화다.

기존 명세에서 후속으로 둔 파일 입력·인코딩을 이 버전에서 구현했고, 실제 제공된 영상에 맞춰 10비트 SDR 입력도 추가했다. 원본의 10비트를 NV12 8비트로 낮추지 않는다. D3D11 content descriptor와 인코더에 실제 유리수 프레임률을 전달한다.

## 단계별 판단

1. 기본 프레임 경로가 검증되어 NVIDIA 확장을 추가했다.
2. 일반 SDR→PQ 지원 조회는 false지만, 지원되는 BT.709 기본 VP 설정에서 확장을 켜면 HDR 결과를 얻었다. 따라서 제품 경로는 불지원 조합 우회에 의존하지 않는다.
3. ON/OFF 회색 ramp의 평균 차이는 약 88코드값이다. ON의 흰색은 PQ 해석에서 약 990~999nit이며 현재 디스플레이 조회값 1000nit와 일관된다. 입력 원색과 중성 패치의 색 좌표도 확인했다. 이것만으로 모든 환경의 색 정확도나 브라우저 동일성을 주장하지 않는다.
4. 공개 렌더러 역시 RTX HDR 경로를 PQ/BT.2020 표시 및 PQ→SDR 보정 대상으로 다룬다. 이 관측과 실제 수치를 근거로 초기 출력 계약을 BT.2020/PQ로 채택했다. [렌더러 표시 경로](https://raw.githubusercontent.com/Aleksoid1978/VideoRenderer/master/Source/DX11VideoProcessor.cpp)
5. 첫 파일 생성 뒤 재디코드 검사에서 색 태그·프레임 수와 GPU 표본 보존을 확인했다. NVENC의 chroma 위치 태그가 left로 남는 문제를 발견해, 실제 2×2 평균에 맞는 center 위치를 HEVC 비트스트림에 명시했다.
6. 실제 사용자 입력이 3840×2160, 72000/1001fps, 10비트 SDR임을 확인하고 P010 입력 경로로 확장했다. 전체 23분 36초 영상의 장시간 변환은 아직 시험하지 않았다. 짧은 실제 입력 결과로 첫 버전을 검증했다.

## 검증된 합성 영상

- 1920×1080, 30fps, 8초, 240프레임, AAC 오디오.
- HEVC Main10, yuv420p10le, BT.2020 / SMPTE ST 2084 / BT.2020 NCL, TV range, center chroma.
- 첫·중간·마지막 재디코드 표본의 평균 오차 약 0.52~0.54코드값. 밝은 평탄 패치의 중앙값 오차는 0.
- 별도 FFmpeg zscale 계산과 RGB→Y′ 행렬 결과가 일치했다. 부동소수 RGB에서 P010으로 자동 포맷 변환을 붙이면 중간 변환이 끼는 것을 발견해, 독립 기준은 zscale의 native planar 10비트 출력으로 비교했다.
- AAC 376개 패킷의 데이터 해시가 모두 일치하며, 오디오·영상 시간 오차는 MKV 밀리초 timebase에 따른 약 0.333ms 이내다.
- 상세 근거: `artifacts/first-test-hdr.mkv.run-47832-284764609/verification.json`.

## 사용자 영상 시험

- 제공된 파일을 읽어 60초 부근의 구간을 패킷 복사로 추출했다. 키프레임 정렬 때문에 발췌 시작은 요청한 60초와 정확히 같지 않다. 원본 파일은 변경하지 않았다.
- 단순 패킷 자르기의 마지막 B프레임들에서 timestamp 간격이 불연속인 것을 발견했다. 이 임시 발췌본 전체를 일정한 프레임률로 취급하지 않고, 연속성이 검증된 첫 432프레임만 `--max-frames 432`로 변환했다.
- 출력: **3840×2160, 72000/1001fps(약 71.928fps), 432프레임, 약 6.006초, HEVC Main10 HDR + AAC**.
- 첫·중간·마지막 프레임의 재디코드 평균 오차는 각각 약 1.09 / 0.072 / 0.299코드값이다. 고주파 경계의 최대 오차는 더 크므로 무손실 출력으로 해석하면 안 된다.
- RGB→Y′ 수치가 독립 zscale 계산과 일치했다. AAC 284개 패킷이 그대로 보존됐고, 오디오 시간 오차는 최대 0.333ms, 영상은 최대 0.5ms다.
- SDR로 톤매핑한 QA 이미지에서 프레임 내용과 색 채널의 정상 출력도 확인했다. 이 이미지는 HDR 모니터에서의 실제 외관을 대신하지 않는다.
- 원래 긴 파일 경로를 실행 파일에 직접 전달하는 별도의 1프레임 실행도 성공했다.
- 이 환경의 현재 처리 속도는 4K에서 약 3fps이며, 23분 전체 변환은 오래 걸릴 수 있다.
- 상세 근거: `artifacts/user-test-hdr.mkv.run-32704-285402203/verification.json`.
- MKV의 나노초 단위 기본 프레임 길이와 밀리초 timebase 때문에 ffprobe의 출력 프레임률 표기는 `21003/292`로 근사된다. 입력의 `72000/1001`과 약 0.000012fps 차이이며, 실제 프레임별 시간은 원래 유리수 프레임률 기준 최대 0.5ms 이내다. 오디오 패킷 경계 때문에 컨테이너 전체 길이는 6.012초로 표시된다.

## 첫 버전 제약

현재 지원은 BT.709 limited의 8/10비트 H.264/HEVC 4:2:0, progressive, 고정 크기·프레임률이다. 그 밖의 입력을 조용히 오해석하지 않고 이유를 안내한다. 임의의 색 태그 누락은 사용자 지정 없이 BT.709로 가정하지 않는다.

인코딩은 손실 압축이며 GPU raw 표본과 모든 픽셀이 동일하지 않다. HDR 정적 mastering metadata나 MaxCLL/MaxFALL은 임의 생성하지 않았다. 브라우저 캡처 비교, NVIDIA App 슬라이더의 반영 여부, 장시간 안정성, 다양한 HDR 표시 환경은 후속 검증이다.

## 다음 개선

사용자가 실제 결과의 밝기·색감을 확인한 다음, GPU 내 RGB→P010 변환과 디코드/인코드 자원 연결로 속도를 개선한다. 이후 일반 UI, 일괄 처리, VFR·비정사각 픽셀·추가 색공간을 확대한다. NVEncC 통합은 계획에 포함하지 않는다.
