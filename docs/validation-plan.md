# 검증 절차와 통과 조건

## 1. 검증의 중심 질문

1. 지원 환경에서 확장 ON이 OFF와 재현 가능한 차이를 만드는가?
2. 그 결과를 화면 표시 없이 텍스처에서 읽을 수 있는가?
3. 출력 코드값을 어떤 색공간으로 해석해야 하는가?
4. 저장·재디코드한 영상이 처리 결과를 보존하는가?
5. 동일 조건의 브라우저 결과와 어느 정도 일치하는가?

아래 기준은 이 프로젝트가 제안하는 초기 판정 규칙이다. NVIDIA가 보장한 정확도 기준이 아니다. 실패를 없애려고 사후에 기준을 느슨하게 바꾸지 않으며, 변경할 경우 이유를 기록한다.

## 2. 실행 기록

각 실행을 독립 디렉터리에 저장한다.

```text
artifacts/<run-id>/
  environment.json
  settings.json
  calls.jsonl
  input.nv12
  frames/off-*.rgb10a2
  frames/on-*.rgb10a2
  frames/*.json
  metrics.csv
  report.md
```

GPU 이름·LUID, 드라이버, Windows 빌드, NVIDIA App 버전과 설정값, HDR 상태, 모니터·연결 구성, 해상도·주사율, 프로그램 빌드 ID, 실행 명령, 입력 해시를 기록한다. 자동 조회하지 못한 값은 수동 기록 또는 unknown으로 남긴다. App 설정은 자동화에 앞서 사용자가 바꾼 값을 기록하는 방식으로 시작한다.

## 3. 시험 데이터

- BT.709 limited NV12의 흑백 계단과 연속 ramp. Y 16/235 경계를 명시한다.
- 중성 회색과 원색·보색 패치. 채널 반전, range 오해를 찾는다.
- 작은 흰 창/큰 흰 창, 저 APL/고 APL, gradient.
- 피부, 낮 장면, 어두운 장면과 광원, 빠른 장면 전환을 포함한 사용 권한 있는 SDR 클립.

패턴은 최소 1080p 전체 프레임으로 구성한다. 단일색 한 픽셀 시험만으로 콘텐츠 적응 처리를 판단하지 않는다. 정지 패턴은 120프레임 반복해 처음 60프레임과 이후 프레임을 분리 분석한다. 60프레임은 초기 워밍업 가정이며 안정화 보장은 아니다. 변동이 지속되면 더 긴 시퀀스와 시간축을 보고한다.

## 4. 핵심 실험 행렬

| 실험 | 고정 조건 | 변경 조건 | 판정 목적 |
|---|---|---|---|
| E01 | 동일 입력·출력 색공간·환경 | 확장 OFF/ON | 실제 효과 후보 확인 |
| E02 | 확장 ON·동일 입력 | App 설정 한 항목씩 | 전역 설정 반영 여부 |
| E03 | 동일 설정·입력 | 새 프로세스 3회 | 재현성·상태 잔류 확인 |
| E04 | 동일 입력·확장 ON | Windows HDR ON/OFF | 표시 환경 의존성 |
| E05 | 동일 입력·확장 ON | offscreen/표시 경로 | offscreen 제약 조사 |
| E06 | 동일 콘텐츠·설정 | 프레임 반복/실제 시퀀스 | 시간적 동작 조사 |
| E07 | 동일 HDR 결과 | P010/직접 RGB 인코딩 | 저장 경로 정확도 |
| E08 | 동일 영상·표시 조건 | Chrome/직접 호출/SDK | 외관·휘도 차이 비교 |

전체 조합을 한 번에 돌리지 않는다. E01/E03을 먼저 수행하고, 결과가 없으면 E04/E05로 범위를 넓힌다. 지원되지 않는 SDR→PQ 조합은 실패로 기록하고, 다른 조합은 별도 실험 ID로 조사한다. 설정 변경 실험은 프로그램 재시작을 기본으로 하며 즉시 반영 여부는 별도 관측한다.

## 5. 비교 방법

### 확장 ON/OFF

두 군 모두 동일한 output color space를 사용한다. 그렇지 않으면 일반 색 변환 차이를 HDR 확장의 효과로 오인할 수 있다.

- 프레임 해시, RGB 코드값 MAE, p95/p99, 패치 중앙값, clipping 비율, 시간별 변화를 계산한다.
- 반복 실행의 자체 변동을 먼저 측정한다.
- 초기 효과 판정: 사전에 고른 밝은 영역에서 ON/OFF 차이가 2개 10비트 코드값과 반복 변동의 5배 중 큰 값보다 크고, 3회 실행에서 같은 경향을 보여야 한다.
- 이 조건은 효과 후보 검출이다. 실제 HDR 의미는 다음 색 검증까지 통과해야 한다. 차이가 작으면 미확정으로 분류하고 다른 콘텐츠·환경을 시험한다.

### 색 해석

- 채널 순서, full/limited range, black/white 위치를 먼저 확인한다.
- PQ 후보 해석으로 패치 휘도와 waveform을 계산하되, 신호가 PQ라는 가정을 보고서에 표시한다.
- 요청한 색공간, 수치 분포, 통제된 HDR 표시 결과가 서로 일관되는지 검토한다. 단일 ramp만으로 내부 transfer를 수학적으로 확정했다고 주장하지 않는다.
- 알려진 코드값을 사용하는 별도 PQ 테스트 프레임으로 분석기와 표시 경로를 교정한다. HDR 알고리즘이 SDR 흰색을 반드시 특정 nit로 옮긴다고 가정하지 않는다.
- 색 의미가 충분히 확인되지 않으면 raw 연구 결과까지만 저장하고 제품용 HDR 인코딩 단계는 보류한다.

### 브라우저·SDK 비교

일반 PNG 스크린샷에는 OS/브라우저 톤매핑이 반영될 수 있다. 먼저 캡처 방식이 HDR/scRGB를 보존하는지, transfer·primaries·스케일이 무엇인지 검증한다. 해석이 불명확한 캡처는 정성 비교에만 쓴다.

같은 영상 프레임, 동일 크기, 같은 모니터·HDR 상태, 같은 설정에서 캡처하고 UI·레터박스를 제외한다. 코드값 비교 전에 동일한 색 표현으로 정규화한다. SDR white level, ICC/색 관리, VSR, 브라우저 버전과 SDK 파라미터를 기록한다.

초기 유사성 목표는 지정 패치의 휘도 오차 중앙값 5% 이내, p95 10% 이내로 제안한다. 1 nit 미만 패치는 절대 오차 0.1 nit 기준을 별도로 쓴다. 측정 불확실성이 이 기준보다 크면 합격 판정을 하지 않는다. 피부·색상 패치와 highlight clipping도 별도로 보고한다.

`Chrome ≈ 직접 호출`과 `Chrome ≠ SDK`가 관측되어도 결론은 해당 환경·설정에서의 출력 차이다. 서로 다른 AI 모델이나 내부 알고리즘을 사용한다는 증거로 확대하지 않는다.

## 6. 단계별 게이트

| 게이트 | 통과 조건 | 실패·미확정 시 조치 |
|---|---|---|
| G0 환경 | 하드웨어 D3D11 장치, 필수 인터페이스·뷰·포맷 조합 확인 | 환경 보고서와 불지원 원인 작성 |
| G1 raw 파이프라인 | OFF 덤프 크기=width×height×4, 채널·행 처리 검증 | readback/업로드 수정 |
| G2 효과 | E01/E03 차이가 반복 변동을 넘고 HDR 후보 특성 관측 | E04/E05, 워밍업·콘텐츠 조건 조사 |
| G3 색 계약 | raw 의미와 표시·분석이 일관됨; 해석 근거 문서화 | 인코딩 보류, 후보 색 해석 비교 |
| G4 저장 | Main10/10비트와 색 태그 확인, 재디코드 패치·range 검증 | 색 변환 또는 인코더 경로 수정 |
| G5 동영상 | 10초→1분→10분 시험, 프레임 누락·중복 없음, A/V 종료 오차 1프레임 이내 | PTS/DTS, drain, 수명 관리 수정 |
| G6 최적화 | 기준 경로 대비 품질 유지, 성능·CPU 왕복·메모리 측정 | 검증된 기준 경로 유지 |

RGB→P010 CPU/GPU 수치 시험은 같은 반올림·필터 조건에서 채널별 1코드값 이내를 초기 기준으로 한다. 손실 압축 이후 전체 픽셀에 이 기준을 적용하지 않는다. 높은 품질의 인코딩 시험에서 평탄 패치의 재디코드 Y′CbCr 중앙값 오차 3코드값 이내를 초기 목표로 두고, 경계 영역은 따로 보고한다.

E08 브라우저 비교는 제품의 재현 목표를 평가하는 별도 조건이다. 캡처 교정이 막혀도 다른 파일 저장 검증은 진행할 수 있지만, 브라우저와 동일하다는 주장은 보류한다.

## 7. 실패 분기

- HRESULT 실패: GUID/payload, 필수 인터페이스, 포맷 조합, GPU 선택부터 확인한다.
- HRESULT 성공·출력 동일: App 토글, Windows HDR, 입력 조건, 프레임 반복, 표시 경로를 순서대로 확인한다.
- offscreen만 실패: 작은 HDR 표시 진단 경로를 추가한다. 표시 시 처리된 텍스처를 읽을 수 있는지도 따로 확인한다.
- 표시 의존성이 남음: 제약이 있는 도구로 진행할지 실험 보고서에서 판단한다. 완전 무인 변환을 지원한다고 표현하지 않는다.
- 출력 회색/어두움: range, 채널 순서, 중복 PQ, primaries, 캡처 톤매핑 순으로 조사한다.
- 직접 RGB 인코딩만 틀림: 명시적 P010 변환 경로를 사용한다.
- 드라이버 버전 변경 후 회귀: 동일 fixture로 재시험하고 검증 버전 목록을 유지한다.

실험 분기를 모두 수행해도 G2가 미확정이면 실패 보고서와 raw 자료를 정리하고 해당 경로의 기능 확장을 중단한다. 검증되지 않은 데이터를 성공한 HDR 변환으로 포장하지 않는다.
